Synthesis

Most likely failure

Guardrails lost to progressive disclosure (F1). The current system's value is enforced discipline (check-ins, hard STOP after each PR, never PR to main mid-review), and it works because CLAUDE.md sits in context on every turn. Skills load their body once at invocation and push detail into reference files loaded late or compacted away in long sessions. This is a structural property of the new architecture, not a contingent event: the first long review session is exposed. Address this first.

Most dangerous failure

Consolidation silently changes the review standard (F3). Merging 3-4 diverging checklist copies plus a mismatched CSV, with no test harness for prompt workflows, can drop checks (the CC BY 4.0 line, UTF-8 checks) or keep the wrong function (compile_citation()). Defects surface months later in published packages with permanent Zenodo DOIs. Irreversible damage to the org's core product. Insure against this with a reconciliation table and a defective fixture package.

The hidden assumption

"Where instructions live doesn't change how they behave." The plan treats the system as documentation to reorganize. It is actually a behavioral program whose enforcement depends on three properties the refactor removes without noticing: instructions that are always in context (CLAUDE.md on every turn), a standard that is pinned per package at review start (the downloaded copy), and stability across a weeks-long stateful review (no mid-review version changes). A second fused assumption: CLAUDE.md is one artifact, when it is two (reviewer workflow + package-resident standards). The refactor correctly centralizes the first and must not delete the second.

Kill criteria

  1. If the read-only prototype skill cannot reliably read plugin reference files while running from a target package directory after one day of testing, stop the plugin approach; instead deduplicate content within the existing command files.
  2. If during the first real plugin-driven review Claude violates a STOP or check-in even once, halt the rollout to colleagues until guardrails are moved into SKILL.md bodies and a blocking hook exists.
  3. If two months after release fewer than half of the active reviewers have installed the plugin, either delete the legacy command files to force the cutover or formally revert to commands; do not run both systems past that date.

Pre-launch checklist

  1. Reconciliation table of all checklist items (4 markdown copies + 27-row CSV) committed and reviewed; every dropped item listed.
  2. Fixture package with planted defects (wrong license, broken citation call, non-UTF-8 text, missing R-CMD-check) passes through the new skill and every defect is caught.
  3. Branch protection enabled on main in openwashdata data package repos.
  4. Full workflow tested from a colleague's machine via the real marketplace install path, not only the maintainer's machine.
  5. Per-package standards file with version stamp is written by review-package and verified present in the fixture run.

Failure modes in detail

F1: Guardrails lost to progressive disclosure

probability: highdamage: high

Enforcement language ("STOP COMPLETELY", check-in points, "always base dev") moved into a shared reference file that skills consult once. After 40+ tool calls the rules were compacted out of context; Claude created a PR and continued into the next review area, then later opened a dev-to-main PR with three unfinished areas. A colleague found autonomous commits and told the team the tool "does whatever it wants now".

Underlying assumption
Behavioral guardrails bind wherever they live; in fact only always-in-context instructions survive long sessions and compaction.
Early warning signs
  • Transcripts where Claude creates a PR and continues without printing the mandated STOP message.
  • PRs with base main, or commits spanning two review areas on one branch.

F2: Reviewers never adopt the plugin

probability: highdamage: high

Marketplace add + install + namespaced commands was more friction than "copy eight files", and the old copied commands kept working. The commands/ directory was kept "just in case", an install error was worked around with "use the old files for now", and October checklist fixes landed only in the plugin. By December, half the org reviewed with stale commands: two visibly different package standards, the exact inconsistency the refactor was meant to end.

Underlying assumption
A technically better distribution mechanism migrates users by itself, without deleting the old path.
Early warning signs
  • Install count stays at one or two while commands/*.md still gets copied.
  • New review issues missing the newest checklist items or using old PR templates.

F3: Consolidation silently changes the standard

probability: medium-highdamage: highest

Merging diverging copies by majority vote made review-package.md canonical for metadata (the one copy missing the CC BY 4.0 check) and took the citation step from review-issue.md (the one copy naming the nonexistent washr::compile_citation()). The CSV was deleted undiffed, losing three items including the UTF-8 check. Smoke-testing on an already-correct package hid everything. Four packages passed review; in January a Zenodo-published package surfaced with License: MIT and a template CITATION.cff.

Underlying assumption
Merging diverging copies is an editorial task you can trust by reading it, rather than a behavioral change needing a diff of every dropped item and a test against a deliberately defective package.
Early warning signs
  • Consolidation PR has no item-by-item reconciliation table; CSV deleted as "unused".
  • Completed-checklist sections in review PRs shorter than the old CLAUDE.md checklist for the same phase.

F4: Platform churn or wrong API details

probability: mediumdamage: medium-high

The plan was built on secondhand research of a fast-moving surface (commands and skills merged in 2025-2026). Frontmatter fields behaved differently than researched; later, a Claude Code update changed path resolution for plugin reference files, and skills started failing mid-workflow, after issues and branches had been created. The single maintainer was in teaching season; reviewers reverted to hand-copying the old CLAUDE.md, leaving two divergent sources of truth.

Underlying assumption
The plugin/skill surface researched in mid-2026 was stable, documented ground rather than a moving target requiring ongoing maintenance.
Early warning signs
  • Frontmatter fields that produce no error but visibly no effect.
  • Claude Code release notes mentioning plugins/skills with no smoke-test afterward.

F5: Over-engineering; refactor stalls half-finished

probability: medium-highdamage: medium

"A weekend of cleanup" became weeks: skill frontmatter, decomposing 632 lines without breaking the stop-after-PR choreography, checklist conflict decisions, marketplace setup. Teaching season froze it with two skills working, others stubbed, and both install paths documented. An onboarding reviewer hit a stubbed skill mid-review and fell back to stale commands. Three packages sat unreviewed; nobody could say which system was canonical.

Underlying assumption
The messy-but-working system was costing more hours than a full migration would consume before teaching season ended.
Early warning signs
  • Two-plus weeks of commits touch only pkgreview infrastructure while zero review issues or PRs open across openwashdata repos.
  • Refactor scope grows (marketplace, versioning, docs) before one skill has replaced its command end to end in a real review.

F6: Untouched state machine, new blame

probability: highdamage: medium

The label-and-branch state machine (labels, issue open/closed state, branch name prefixes, standing dev branch) is what actually breaks: a colleague tidied labels and create-next-issue made a duplicate; a manually closed issue plus an unprefixed branch made review-complete refuse opaquely; dev diverged from main after a hotfix. All pre-existing fragilities, but every failure now carried the plugin's name, and reviewers concluded the new system was worse.

Underlying assumption
The state machine's known fragilities were tolerable as-is, and only the packaging needed fixing.
Early warning signs
  • First duplicate issue created after a manual label or issue edit.
  • Bug reports against the plugin for failures that predate it.

F7: Per-package CLAUDE.md was load-bearing

probability: mediumdamage: high

The downloaded CLAUDE.md was two things fused: reviewer workflow and package-resident standards. The refactor deleted both from packages. A student contributor later opened Claude in a reviewed package; with no CLAUDE.md, Claude moved vignettes out of articles/ and rewrote _pkgdown.yml, dropping Plausible analytics and the ETH funding sidebar; the PR was merged and analytics silently stopped. Nobody could later tell which standard version a 2026 package had been reviewed against.

Underlying assumption
CLAUDE.md's only consumer was the reviewer running the slash commands, when its real consumers were every future Claude session inside the reviewed package.
Early warning signs
  • First post-refactor PR in a reviewed package touching _pkgdown.yml or vignettes/ paths.
  • Plugin reference files edited with no corresponding version marker in any reviewed package.

F8: Version skew on in-flight reviews (counter-check finding)

probability: mediumdamage: high

A review is a weeks-long stateful process, not a session. The old downloaded CLAUDE.md accidentally pinned the standard at review start; the plugin deliberately removes that pinning. A v1.3 checklist rewording landed while three reviews were mid-flight on v1.2-format issues: create-next-issue could not reconcile old issue bodies, created a duplicate, and forked the state machine, while a never-updated reviewer applied the old standard in the same month. The plan versions the tooling but never versions the review.

Underlying assumption
"One source of truth" and "reviews that span weeks across multiple users" are compatible without a pinning or migration story.
Early warning signs
  • A plugin release merged while any pkgreview-* labeled issue is open, with no note on which reviews it applies to.
  • First create-next-issue or review-status run that misreads an issue created by an earlier plugin version.
